Ukiyo E-commerce Front-End Architecture Plan
Overview & Tech Stack
Ukiyo is a mobile-first, functional-luxury e-commerce site targeting Indian women (26–45) in urban centers. The front-end will be built with React and Next.js to leverage server-side rendering (SSR) and static generation for performance and SEO[1]. We will use TanStack React Query for efficient data fetching and caching[1], ensuring the UI remains responsive even on slow networks. Development follows a mobile-first approach, prioritizing smaller screens for design and performance[2]. This means using fluid, responsive layouts and optimized assets for mobile, then enhancing for larger devices. The site’s aesthetic will mirror high-end brands (e.g. Pas Normal Studios, Gucci) – clean design, strong typography, and subtle interactions that convey a premium feel. We’ll avoid clutter and excessive promotion on the landing page to maintain an elegant vibe (e.g. keeping “Sale” content in a separate section to preserve the premium brand image[3]). The overall tech stack and approach can be summarized as:
•	Next.js & React – for SSR/SSG, routing, and performance optimizations (code-splitting, image optimization, etc).
•	TypeScript – to improve code reliability and maintainability[1].
•	TanStack Query – for server-state management (products, cart, etc.), offering caching, background updates, and easy integrations with Next SSR[1].
•	CSS/Styling – using a modern utility-first CSS framework or CSS-in-JS for responsive design (e.g. Tailwind CSS or styled-components), ensuring consistency with the functional-luxury tone.
•	OAuth & Auth Library – NextAuth.js or similar for Google/Apple login, plus a custom solution for phone OTP authentication (backed by an SMS service).
UI/UX Design Considerations
Mobile-First UX: We will design layouts that look and work great on mobile devices first, then scale up. Navigation will be mobile-friendly – e.g. a hamburger menu and drawer for categories/filters on small screens (as opposed to hover-based menus that work on desktop)[3]. All pages will be fully responsive, using flexible grids and media queries so that content (images, text) adapts gracefully to different screen sizes[2]. Google prioritizes mobile-friendly sites, so this approach also boosts SEO[2].
Login and Personalization: Users can browse the catalog and product details without logging in. However, certain actions (adding to Bag or Wishlist, or using personalization features like setting skin tone or body shape) will prompt login. The UI will incorporate friendly nudges instead of roadblocks. For example, if a guest user adds an item to the wishlist, we’ll show a temporary save with a header message like “Your items are saved temporarily; please log in or register to save them”[4]. This indicates the item is saved only for the session, encouraging sign-up without forcing it. Similarly, if a guest adds items to the bag, they can proceed to checkout as a guest, but with reminders that logging in will save their bag across devices[5]. A dynamic notification like “Items saved temporarily. Log in to save permanently” will be shown in the header area whenever the user has unsaved bag/wishlist items[4]. Once logged in, the header can change to confirm their items are saved to their account.
Functional-Luxury Tone: The UI will balance functionality (clear navigation, easy filtering, fast checkout) with a luxury feel (spacious layout, high-quality imagery, minimalistic icons). We’ll avoid flashy banners or cluttered discount tags on every item, as that can cheapen the experience[3]. Instead, any promotional offers will be subtle or confined to a dedicated “Sale” section[3]. Typography will be chosen to reflect elegance – for example, a clean sans-serif for body text and a refined display font for headings or the logo (as hinted by brand guidelines). Interactive elements (buttons, hover states, transitions) will be smooth and understated to convey polish. We’ll ensure important CTAs (Add to Bag, Buy Now) are prominent but styled in line with the brand (e.g. using a distinctive brand color, but with a clean design).
Ease of Use: Navigating Ukiyo should feel intuitive. The menu will likely include categories like New Arrivals, Clothing, Accessories, etc., and on mobile this will slide out as a drawer menu[3]. Search functionality will be accessible (e.g. a search icon on the header). Filters will be easy to apply and clear (with reset options), as detailed below. Throughout the user journey, we aim to reduce friction – e.g. allow “Continue as Guest” in checkout with minimal required info[6], use address auto-complete APIs to speed up form filling, and provide helpful defaults (like showing previously used addresses or payment methods for logged-in users). We will also incorporate personalization gracefully: logged-in users can set preferences (skin tone, body shape, etc.) in their profile, and the UI can use these to tailor the experience (for instance, filtering products or selecting model images that match the user’s profile by default). These personalization features will be clearly opt-in and transparent to avoid any privacy concerns.
Finally, accessibility will be a priority: proper alt text on images, keyboard-navigable components, and readable font sizes will be used to ensure the site is usable by all customers.
Key UI Components & Pages
Landing Page (Home)
The landing page is designed to make a strong first impression and quickly inform users about Ukiyo’s offerings and values. Key components of the landing page include:
•	Hero Banner: A full-width hero section at the top, featuring either a high-quality image or slider showcasing a signature product or campaign. It will include a tagline or message that reflects Ukiyo’s brand (functional-luxury vibe) and a clear call-to-action (e.g. “Shop New Arrivals”). The hero should be responsive, perhaps showing a centered crop on mobile and a wider panorama on desktop.
•	New Arrivals Carousel/Grid: A section highlighting the latest products. On mobile, this might be a horizontal scrollable carousel of product cards (each showing a product image, name, and price). On larger screens, it could display as a grid of new items. This section entices users to explore fresh inventory right away.
•	Value Proposition Section: A brief showcase of what makes Ukiyo unique. This could be a three-column layout (stacked vertically on mobile) with icons or images and text, highlighting points like “Premium Quality Fabric,” “Customized Fit Advice,” or “Free Returns”. These build trust and align with the functional-luxury tone by emphasizing quality and service.
•	Featured Collections/Stories: Optionally, the landing page can have tiles or banners linking to specific collections (e.g. Autumn Collection, Workwear Edit) or a journal/blog snippet if relevant. Given the luxury angle, we might include an editorial-style component (like a beautiful lookbook image that links to a “Ukiyo Studio” or styling tips section).
•	Navigation & Footer: Although common to all pages via layout, the landing page will prominently feature the site header (with logo, menu, search, account, and bag icons). The header will use a sticky design on mobile for easy access. The footer will include standard links (customer service, social media, etc.) in a clean layout.
Performance considerations: The hero image will use Next.js optimized <Image> component for responsive loading. We’ll lazy-load below-the-fold images (e.g. product carousels) so that initial load remains quick. Critical content (hero text, navigation) will be rendered server-side so users see something immediately on load. We may also prefetch data for featured sections during SSR to avoid loading spinners on the landing page.
Product Catalogue & Filtering (Product Listing Page)
The product catalogue page (also called Product Listing Page, PLP) displays a list of products with the ability to filter and sort them. This page must be highly performant and easy to navigate, as users may spend a lot of time browsing here. Key features and components:
•	Product Grid: The main content is a grid of product cards showing each item’s thumbnail, name, price, and maybe a quick indicator if multiple colors are available. On mobile, this grid will likely be 2 columns; on desktop, 3-4 columns. Each product card is a reusable component (with an image that uses Next/image for optimization, and actions like “quick view” or “add to wishlist” if applicable).
•	Filters Sidebar/Drawer: Users can filter products by skin tone, body shape, fabric type, occasion, etc., as specified. On desktop, filters can appear in a sidebar to the left of the grid. On mobile, clicking a “Filter” button will open a full-screen drawer or modal with filter options (since sidebars don’t work on small screens)[7]. Filters will likely be a combination of checkboxes (for multi-select categories like fabric type or occasion), dropdowns or buttons for selections like skin tone or body shape, and range sliders if needed (e.g. price range, though not explicitly mentioned). Each filter category will be collapsible for a clean look.
•	Filter State & URL: We plan to reflect filter selections in the URL query parameters (e.g. ?skintone=medium&occasion=party) so that filter results can be sharable and bookmarkable. This approach also improves SEO and performance – crawlers can index filtered pages, and the app can parse the URL to know what to fetch[8]. By driving the filtering via URL parameters, we avoid excessive client-side state complexity and ensure the filtering is source-of-truth in the URL (users can hit “back” to remove a filter, etc.)[8]. For example, selecting “Skin Tone: Medium” and “Occasion: Festive” would update the URL and trigger a data fetch for products matching those criteria.
•	TanStack Query for Data: The product list will be fetched via an API call (likely to a Next.js API route or a headless CMS/commerce backend). We use TanStack Query’s useQuery hook to fetch and cache the results for a given filter set. For instance, useQuery(['products', filters], fetchProducts) will fetch products for the current filter combination. If the user toggles a filter, the query key changes and TanStack Query triggers a new fetch. It will cache results so that if a user toggles filters back and forth, previously fetched data can be shown instantly from cache. We can also leverage TanStack Query’s features like request debouncing to wait for the user to finish selecting filters (e.g. apply a slight delay after the last change before fetching) – this avoids flicker and unnecessary calls, which is great for UX[9][10].
•	Sorting and Pagination: Although not explicitly listed, a catalogue page typically has sorting (e.g. by price, popularity) and pagination or infinite scroll. We will include a sort dropdown and perhaps implement infinite scrolling or “Load more” button instead of classic pagination for a smoother experience on mobile. TanStack Query can be extended to use infinite query patterns if needed (to fetch the next page of results).
•	SEO & SSR: The catalogue page will use Next.js to pre-render content. For a generic listing (e.g. all products or top categories), we may use Static Generation. For filtered pages, we can server-side render based on the query params. Using Next’s data fetching (getServerSideProps or the newer app/ route handlers), we can prefetch product data for the initial load, and then hydrate it into TanStack Query’s cache on the client[11][12]. This means a user clicking a link to a filtered page sees products directly in the HTML from the server, and then React takes over for interactivity. The pre-rendered approach combined with URL-based filters yields benefits mentioned earlier: shareable filter links, crawlable content, and a fast initial page load[8].
Code Snippet – Example Filter Hookup: Below is a simplified example of how the catalogue might use TanStack Query to load filtered products, with filters stored in URL query parameters (accessible via Next.js router).
import { useQuery } from '@tanstack/react-query';
import { useRouter } from 'next/router';

function ProductListPage() {
  const router = useRouter();
  const filters = router.query; // an object like { skinTone: 'medium', occasion: 'party', ... }

  // Fetch products based on current filters
  const { data: products, isLoading } = useQuery(
    ['products', filters], 
    () => fetch(`/api/products?${new URLSearchParams(filters as any)}`).then(res => res.json())
  );

  // ... render the products grid and a filter button
}
In practice, the filters might be managed through a dedicated state as well (especially on client side when adjusting filters without full page reload), but the concept is that the URL and query key drive the data. The fetchProducts API would apply the filters server-side (e.g. database query). We also would handle loading states and errors gracefully in the UI (showing a spinner or message if no products found).
Product Detail Page (PDP)
The Product Detail Page presents all information about a specific product and helps convert browsers into buyers. For Ukiyo’s PDP, we’ll implement:
•	Product Media Gallery: At the top, a carousel or gallery of product images (and possibly videos). Users can swipe through images on mobile or click thumbnails. We might include a feature to view the image full-screen. If multiple variants (colors) exist, the gallery might update to show the selected variant’s images. Using Next.js image optimization here will ensure even high-resolution images are delivered in the appropriate size for the device.
•	Product Info Section: This includes the product title, description, price, available sizes, and an Add to Bag button. Size selection could be via buttons or a dropdown. Given the target user, we should include guidance on sizing – e.g. a size chart or a recommendation engine (like “Your usual size: M” if personalization knows their measurements). There might also be an option to select quantity. The design will emphasize the product name and price with clear typography, and the Add to Bag button will be prominent. If an item is out of stock in some size, we’ll show a “Notify me when available” link for logged-in users, which can capture their email/phone for alerts.
•	Pairing Recommendations (Ukiyo Stylist): A distinctive feature will be a “Pair With” or “Complete the Look” section on the PDP. This addresses the user question of “What do I pair it with?”[13] by showing a few items that complement the current product. For example, if the user is viewing a blouse, the page might recommend a skirt or accessories that go well with it. This will be implemented as a horizontal carousel of product cards (possibly reusing the ProductCard component) under a heading like “You could pair this with…”. The recommendations data can be fetched via an API (e.g., /api/products/{id}/recommendations). We’ll fetch and cache this with TanStack Query as well, keyed by product ID. The component should be modular, as noted in planning, so it can also appear on the Wishlist or Bag pages[14] (e.g., showing outfit suggestions based on items in the bag).
•	Try-On Visualizer (Placeholder): Ukiyo plans a “See how it looks on you” feature (augmented reality or AI-driven)[15]. For now, we will include a placeholder for this Ukiyo Studio try-on feature. This could be a button or section like “👗 Virtual Try-On (Coming Soon)” where eventually a user might upload a photo or use AR to see the item on themselves. In this version, clicking it might open a modal with a static image or message that the feature is in development. However, we will structure the code so that the try-on component is lazy-loaded only when needed (since any AR or heavy AI component could bloat the bundle). For example, the try-on interface (if implemented) might be a separate dynamic import: const TryOnModule = dynamic(() => import('../components/TryOnModule'), { ssr: false });. This ensures it doesn’t affect initial page load.
•	Reviews and Details: (Not explicitly mentioned, but often present) – We might include an accordion or tabbed section for additional details like product details (fabric, care instructions) and customer reviews. These add credibility and information for the customer’s decision-making. This content can be static or fetched as needed.
Personalization on PDP: If the user has provided their skin tone or body shape in their profile, the PDP can use that info to enhance the experience. For instance, if multiple product images are available with models of different skin tones or body types, we could default to the image closest to the user’s profile (a future feature). Or if the user’s height is known, we could show an approximate fit guidance (“Hemline will reach your knees based on your 5’4” height”). These are future personalizations – for now, we ensure the design can accommodate such info (maybe a section for “Model is 5’8” wearing M size” and possibly “On you, this may fit as …” when data is available). Structurally, we’ll prepare to fetch user-specific recommendations via an API (e.g., /api/personalize/{productId}) which currently returns nothing or defaults, but can later be implemented with real logic.

Bag & Wishlist
These components handle the user’s intended purchases and saved favorites. They have similar behavior in prompting login and saving items.
Bag (Shopping Cart):
- The Bag page (or drawer, if we implement it as a sidebar cart) shows all items the user intends to buy. For each product, we display a thumbnail, name, size, quantity selector, and price. Users can adjust quantity or remove items. We’ll also show a summary with subtotal, any applied discounts, and the final total. A “Checkout” button will proceed to the checkout flow.
- If the user is not logged in, items in the bag are stored locally (e.g., in a cookie or localStorage, or just in React state). We do not require login to add to bag (to keep browsing friction low), but we will remind them that their bag is temporary. As noted, a banner like “Items saved temporarily – log in to save them across devices” will be shown[5]. We might also show a small icon or message on each item in the bag indicating it’s not saved to an account yet.
- Once the user logs in (during checkout or before), we will merge the local bag with their server-side bag. The app will call a cart API to sync items. The login flow can redirect back to the bag or checkout with state preserved. If continuing as guest, the user can still check out, but we will ask for an email in checkout to send order confirmation and give an option to create an account afterward.
- Pair-With in Bag: We can reuse the “Pair With” recommendations here as well[14]. For example, if the bag contains a top, the bag page might show “Complete your look” suggestions (maybe based on the first item or all items in cart). This is a nice value-add to increase AOV (Average Order Value) and it aligns with Ukiyo’s stylist experience. Implementation-wise, we can call a similar recommendation API with all cart items as context. For now, it could simply recommend items related to the first item in the bag.
Wishlist (Favourites):
- The Wishlist page (or component) lists all products the user has favorited. Each item shows a thumbnail, name, price, and an “Add to Bag” button for quick action. Users often build a wishlist to save items for later or compare.
- Login Requirement: We will allow users to click the “heart” icon to favorite items even without logging in, but handle it similarly to the bag: show them it’s a temporary save. On adding the first item to favorites as a guest, we’ll display a message/bar: “Your items are saved temporarily; please log in or register to save them”[4]. If they never log in, the wishlist could be stored in localStorage for the session, but they risk losing it if they clear data or switch devices. The UI will remind them of this. If they choose to log in, we’ll persist those wishlist items to their account (via an API call).
- Wishlist functionality will include removing items and possibly moving items to bag. Also, a “Add All to Bag” option can be provided for convenience (if the user wants to purchase everything in the wishlist)[16]. This bulk action will be available on the wishlist page for logged-in users.
- Pair-With in Wishlist: The wishlist can also utilize the pairing feature – for example, if you have a skirt in wishlist, it could show a top that goes well with it (maybe one that’s also in your wishlist or a new suggestion). This would use the same modular component for recommendations.
Under the hood, state management for Bag and Wishlist will partially use TanStack Query and partially React Context or local state. For example, for a logged-in user, the bag and wishlist data can be fetched from an API (/api/cart, /api/wishlist) and stored via useQuery (with mutations for adding/removing items). For a guest user, we might manage the cart in a Context that persists to localStorage. We will unify these via a custom hook or context that abstracts whether the user is logged in or not. That way, components can call something like addToCart(product) without worrying about auth state – the function will either call the API or update localStorage accordingly and update the UI state.
Prompting Login: At various points, when a guest user tries to perform an action that requires login (saving beyond session, proceeding to checkout to save address, etc.), we’ll use modals or redirect flows to the login page with redirect-back. For example, clicking “Save to Wishlist” as guest could trigger a popup: “Log in to save your favorites,” with quick buttons to log in via Google/Apple or continue as guest (with the understanding it’s temporary). This gentle prompt aligns with avoiding forcing phone/email upfront (a noted pain point with some Indian e-commerce sites)[17].
Login/Signup & Authentication
For authentication, we will provide a unified Login/Signup experience with multiple methods: Google OAuth, Apple Sign-in, Phone Number OTP, and Email[18]. The UI will likely be a dedicated page (or modal) where the user can choose their method: e.g. a set of buttons “Continue with Google”, “Continue with Apple”, etc., and an option to use email/phone. Key points:
•	OAuth (Google/Apple): Using NextAuth.js or a similar library, we can implement Google and Apple providers easily. The user clicks the button, goes through the OAuth flow, and is returned with a session. This is seamless and highly recommended for a luxury brand because it’s quick and doesn’t ask the user to fill a lot of fields. We’ll ensure to request only minimal scopes (basic profile info).
•	Phone Number (OTP): Many Indian users prefer phone-based login. We will design a flow where the user enters their mobile number, clicks “Send OTP”, enters the code, and gets logged in. This requires a backend integration (e.g. Firebase Auth, AWS SNS, or an SMS API) to send and verify OTP. In our front-end plan, we include a placeholder function that calls something like POST /api/send-otp and POST /api/verify-otp. On success, the user is considered authenticated. We might choose to treat phone login separately or integrate with NextAuth via credentials provider. UI-wise, we have to handle input and validation states.
•	Email (Magic link or password): Given modern trends, we might avoid implementing a full password system and instead use email magic links (login via a link emailed to the user) or an OTP to email. However, if needed, we can also allow a traditional email/password signup. For now, we’ll likely stick to passwordless for simplicity (one less thing to secure).
•	Profile Completion: After the initial OAuth/OTP, if it’s a new user, we can prompt them to complete profile details (like name, and optional fields like skin tone, body shape, etc.). This could be done on a “Welcome” screen or in the user account page. It’s not mandatory to use the site, but since personalization features rely on these, we’ll invite users to fill them. For instance, “Complete your profile to get personalized size and style recommendations.”
The authentication state will be stored in a global context or via NextAuth’s provider. We’ll wrap our app with an <AuthProvider> so any component can know if the user is logged in and access their basic info. Secured API routes (like /api/cart or /api/checkout) will verify the session token.
Admin Access: The login system will also distinguish admin users. Admins might log in through a special route or via the same system but with an account marked as admin. We’ll likely have a specific admin login page if needed. But using the same OAuth (Google) with a specific allowed Google account for admin could be a simple approach. In any case, after login, the app can check a user profile field like role: 'admin' to grant access to admin panel routes.
Checkout & Address Flow
The checkout process will be implemented as a multi-step form to keep it user-friendly, especially on mobile where long forms can be daunting. We will include the following steps/components, ensuring that guest checkout is possible:
1.	Contact Information: (Only for guest users) – If the user is not logged in, the first step is to ask for an email (to send order confirmation and updates). We’ll also offer a “Login for faster checkout” prompt here as a last attempt to get them signed in (since logged-in users can have saved addresses/payment). However, the user can continue as guest by providing an email. This step is skipped or pre-filled if the user is logged in.
2.	Shipping Address: A form to collect the recipient’s name, address, pincode, city, state, and phone number. We should integrate a pincode lookup or address auto-complete to simplify this (e.g., using Google Places API for address auto-completion or an Indian pincode database for city/state auto-fill when pincode is entered). For logged-in users, if they have saved addresses, they can choose one or add a new address. This page needs to be mobile-optimized (use of dropdowns for state, numeric keypad for phone, etc.). We will validate for correct formats and provide helpful errors.
3.	Shipping Method: Depending on business logic, if there are multiple shipping options (standard, express), we present them. This might be a simple selection if needed. (If all shipping is standard/free, this step might be omitted).
4.	Payment Method: Integration with a payment gateway (e.g., Razorpay, Stripe) will happen here. Since this is front-end architecture, we’ll include a placeholder for payment processing. Possibly a button like “Pay Now” that triggers the gateway’s checkout modal. We’ll ensure that required details from previous steps are collected before enabling payment. For guest users, we will definitely need the email from step 1 and address from step 2 prior to payment.
5.	Order Review & Confirmation: Before final submission, show an order summary: items with their prices, shipping cost, total, and shipping address. User can confirm everything looks right. Then clicking “Place Order” will finalize the purchase. After a successful payment, we’ll show an Order Confirmation page, which thanks the user and shows an order number and summary. This page might also invite the user to create an account if they checked out as guest (e.g., “Create an account to track your order and save your details for next time.”). It will automatically redirect to the home or orders page after some seconds (as noted in flows[19]).
Guest vs Logged-in differences: As mentioned, logged-in users can have saved info (so their flow might be faster – e.g., skip contact info, choose saved address, perhaps even saved payment if tokenized). Guests have to fill everything, but we minimize what we ask: we won’t force account creation, only the necessary details to fulfill the order[6].
We will implement the checkout as its own section in the app, possibly using a wizard-like UI (show steps progress at top). In Next.js, this could be a single checkout page that manages state for all steps, or multiple sub-routes (/checkout/address, /checkout/payment, etc.). We might lean towards a single page with conditional rendering per step for simplicity, since form state often spans steps. State can be managed with a combination of local state and context (for multi-step memory). For example, we may have a CheckoutProvider that stores the user’s form data as they go, so if they navigate back a step, their inputs persist.
On form submission, the front-end will call a placeholder API route (e.g. POST /api/checkout) with all the order info. That backend will handle creating the order and initiating payment. For now, we’ll simulate this with dummy success response. The architecture, however, is ready to integrate an actual payment gateway. We also plan to make the checkout as smooth as possible – e.g., disable the “Place Order” button and show a spinner while payment is processing to avoid duplicate submissions.
Admin Panel (Inventory, Analytics, Returns)
In addition to customer-facing pages, Ukiyo requires an Admin panel that is accessible only by authorized staff. We will incorporate the admin interface within the same Next.js app, but under protected routes. The admin area will have its own navigation and pages for managing the store:
•	Authentication & Authorization: Only users with an admin role can access the admin pages. We will protect these routes using Next.js middleware or server-side checks. For example, if using Next’s pages directory, we can add a check in getServerSideProps for admin pages to verify an admin session, otherwise redirect to login. In the app directory, we can use a React context or a higher-order component to guard admin routes, and possibly Next 13’s middleware (which runs before routing) to block unauthorized access. The login system might allow an admin to log in via the regular UI, but we might also implement a separate admin login if needed (e.g. a different client ID for Google OAuth limited to company domain). For now, assume the same login and just role-check.
•	Admin UI Layout: We can create an AdminLayout component that wraps all admin pages, providing a sidebar or header specific to admin (with links to Inventory, Analytics, Returns, etc.). This layout will load only for /admin routes. We might style it differently (since admins care more about data density than luxury feel, but we’ll keep it clean and functional).
•	Inventory Management: An admin page to list products and allow creating/editing them. Likely a table of products (with columns like name, stock, price, etc.) and actions to edit or delete. We might use a library or component for tables (TanStack Table could be a candidate, or a simple HTML table for now). Editing/adding can be a form page or modal. Since this is an internal tool, we prioritize function: e.g., allow uploading images, entering product metadata. This page will fetch product data via an authenticated API (only accessible to admins). We will use TanStack Query here too for data fetching and mutations (e.g., useQuery(['allProducts'], fetchAllProducts) and useMutation for updates). Caching might not be as crucial here, but it can still help to reflect edits instantly (optimistic updates).
•	Analytics Dashboard: A page for key metrics – e.g., sales over time, user signups, popular products. We might integrate a chart library for visualizations. For this plan, we note that we will fetch aggregated data from an /api/admin/analytics endpoint. The UI might display cards with totals (total sales today, etc.) and charts (sales trend, etc.). We will ensure this page is also mobile-friendly (though admins might mostly use desktop, we won’t assume that).
•	Returns Management: A page where admins can see return requests and update their status. This could be a list of orders that have return initiated, with details like order ID, items, reason, status (pending/approved/processed). Admin can click to view details and mark as processed or provide a response. This is essentially a CRUD interface similar to inventory but for returns.
All admin pages require being logged in as admin. If a non-admin or not logged user attempts to access, they should be redirected to the main site or a login page. In code, we might implement a Next.js middleware (middleware.ts) that checks req.nextUrl.pathname.startsWith('/admin'). If so, and if the user is not an admin (we’d check a cookie or token for admin status), we respond with a redirect to / or an admin-login. This ensures security at the edge. Additionally, each admin API route will double-check credentials server-side.
We anticipate building the admin as a part of the Next.js app (monolithic) for simplicity, hosted on the same domain but under /admin. This is feasible with Next and allows code sharing (e.g., using the same components like tables or forms). For example, the product form component could be reused between the customer site (if there’s a “Submit design” feature someday) and admin panel.
Citing the Plan: The requirement for admin pages (inventory, analytics, returns) is clearly part of Ukiyo’s scope[20]. By implementing them as described, we ensure the front-end covers base management features needed by day 100.
State Management & Data Flow
We will use a combination of TanStack React Query, React Context, and local component state to manage data and UI state:
•	Server State (Data from APIs): TanStack Query is the primary tool here. All asynchronous data – product lists, product details, cart contents (for logged-in users), wishlist items, recommendations, etc. – will be retrieved with useQuery or useMutation. This gives us caching, automatic refetch on re-focus, and deduplication. For example, if the user visits a product page, useQuery(['product', id], fetchProduct) provides the data. If they then go to the catalog, which also fetches that product as part of a list, React Query can serve it from cache if still fresh. This reduces network calls and improves perceived speed[21]. Additionally, React Query’s devtools will help us monitor query cache during development for fine-tuning.
•	Global Client State (Auth & User Info): For things like the current logged-in user and their personalization settings, we’ll use a Context or the state management provided by our auth library. NextAuth, if used, comes with a useSession() hook to get the current user data. We might create a custom AuthContext that provides user info and methods (login, logout). This context wraps the app so that components like Header can display the user’s name or login button depending on auth state. Similarly, for personalization data (skin tone, etc.), once the user is logged in, we will fetch their profile (perhaps via React Query) and store it in a context or global store so that multiple components can use it (e.g., filters might read the user’s preferred skin tone to perhaps highlight those options).
•	Local UI State: We will manage component-specific state (like a modal open/close, form inputs, etc.) with React’s useState or useReducer as appropriate. For instance, whether the filters drawer is open is local to the catalogue page component. The checkout form data across steps might use a useReducer to handle complex updates in one state object, or Context if steps are separate components.
•	State Hydration (SSR to CSR): Because we’re using Next.js SSR for initial data, we’ll leverage Query hydration. On the server, we will prefetch critical queries and pass them via dehydratedState to the client[11][12]. For example, in getServerSideProps for the product page, we fetch the product and perhaps recommendations. We then hydrate those into React Query cache on the client, so the page loads instantly with data. We’ll set appropriate staleTimes on queries (e.g., product data might be semi-static, so can be cached longer; cart data should refetch often).
•	Error Handling: We will globally handle errors from API calls. E.g., if a fetch fails (network error), React Query will by default retry, but we will also show a user-friendly message or toast. A error boundary or toast system (like using a library or custom component) will be in place. For auth errors (like session expired), we can catch those in a response interceptor and redirect to login.
Overall, TanStack Query will simplify a lot of state handling (no need to manually store lists in global Redux or so), and Context will handle cross-cutting state (auth, theme). This architecture avoids heavy use of Redux or MobX, leaning on modern React patterns and the robust caching library[21] for a cleaner, more maintainable codebase.
Performance Optimizations (SSR, Caching, Lazy Loading)
Performance is crucial, especially given the mobile-first audience and SEO needs:
•	Server-Side Rendering & Static Generation: We will use SSR/SSG intelligently to ensure fast initial loads. Key pages like Landing, Product Catalog, and PDP will be pre-rendered. For example, the landing page can be statically generated (since content changes are infrequent) and revalidated periodically. Product pages might use Incremental Static Regeneration so that we can cache them and only update after product changes. Catalog pages with filters will use SSR for the first request (especially if coming from an external link) so that the user sees results immediately. According to Next.js best practices, using SSR/SSG not only improves user experience but also SEO by serving full HTML content to crawlers[22][23]. We’ll choose SSR for pages that depend on user-specific or frequently changing data (like an account page or dynamic search results) and SSG for largely static content (maybe a category with rarely changing lineup).
•	Code Splitting & Lazy Loading: Next.js automatically code-splits each page, but we will further split large components. As mentioned, heavy optional components (e.g., a hypothetical AR try-on module, or an analytics chart library in admin) will be dynamically imported only when needed. This keeps the initial JS bundle light. We will also lazy-load images outside the viewport using Next/image’s loading="lazy" (which is default for offscreen images). For third-party scripts (like payment gateway or analytics), we’ll load them asynchronously and only on relevant pages.
•	Caching & CDN: We will use caching at multiple levels. Next.js pages can be cached on the Vercel edge or CDN so that repeat visits are extremely fast. Our TanStack Query cache prevents refetching of data that hasn’t changed. We might also implement HTTP caching for certain APIs (like product detail API responses could have a short-term cache header if they rarely change). Static assets (images, fonts) will be served via Next’s static pipeline and cached by the CDN.
•	TanStack Query Caching: As described, TanStack Query gives us in-memory caching of data. For instance, if a user views a PDP then goes back to the catalog, the product list can be served from cache (especially if the query keys overlap or if we prefetch some data). We might prefetch some queries for smoother navigation – e.g., when user hovers over a product link, prefetch that product’s data. React Query’s prefetch capabilities can help implement such instant navigations. Also, since TanStack Query avoids redundant calls (if data is fresh), it indirectly improves performance by reducing server load and payload.
•	Optimized Assets: We’ll utilize Next.js features like Image Optimization (serving responsive, webp images) and Font Optimization. We may self-host fonts or use a fast provider, and configure next.config.js to enable font optimization to avoid layout shifts[24]. All CSS will be optimized (Tailwind purging unused styles or minified CSS). We will also strive to keep our JS bundle size small by only importing what we need (avoiding large dependency bloat). Monitoring with Lighthouse and Next.js analytics will guide further optimizations.
In summary, by combining SSR for initial payload, careful data fetching with caching, and splitting/lazy-loading, Ukiyo’s front-end will achieve fast load times and smooth interactions, even on mobile internet. This aligns with both user experience best practices and SEO needs (fast and mobile-friendly)[25][2].

Component Hierarchy & Reusability: The app is broken into modular components as listed. For instance, the Header component is used on all pages (imported in the root layout). The HeroBanner, NewArrivals, ValueProps components make up parts of the Landing page. The ProductCard is reused in catalog, recommendations carousel, and maybe wishlist (with minor variations if needed). The FiltersSidebar and FiltersDrawer use a common set of filter controls but rendered in different containers depending on viewport. The PDP uses specialized components like ProductGallery and Recommendations which themselves use generic components like ProductCard internally. Auth components are used on the Login/Signup pages or modals. The Checkout components are used within the checkout page to break the steps. The admin components (tables, forms) are separate to avoid bloating customer bundle (and can be code-split to only load for admin routes).
State & Data Flow in Architecture: Context providers (AuthContext, possibly CartContext) will wrap relevant sections. For example, we might wrap the entire app in AuthContext at _app (or Root layout in app directory). CartContext might wrap only the parts needed if using context for guest cart, though we can also just use React Query for cart for logged in and local state for guest. The components will get data either from context (e.g., useAuth() to know if user is logged in) or via props. We’ll mostly pass data via props for composability (e.g., ProductCard gets a product object prop). For cross-component communication, lifting state up or context will be used where appropriate (for example, a filter component updating filters might use router to update URL or call a context method).
SSR and Routing Structure: Each page route (like /products/[id]) corresponds to a React component that may fetch data. With Next.js 13, we can do data fetching in a React Server Component for initial load and then augment with client components where needed. For instance, the product listing page could be mostly a Server Component that fetches products (for initial render) and includes a client component for the interactive filter controls (which then use React Query to refetch on changes). This hybrid approach is possible but for conceptual clarity we can assume a more classic approach: fetch on server via getServerSideProps and hydrate.
Placeholder API Integration: The folder structure includes an /api directory to illustrate Next.js API routes (or route handlers). We will create stubs for critical APIs: - GET /api/products (with filters) – returns product list (later connected to a database). - GET /api/products/[id] – returns product details. - GET /api/products/[id]/recommendations – returns an array of related products (stubbed logic for now). - POST /api/cart & GET /api/cart – for managing cart items (for logged-in users, tied to user session). - POST /api/wishlist & GET /api/wishlist – for wishlist management. - POST /api/auth/[...] – NextAuth routes or custom routes for login (Google, Apple will be handled by NextAuth internally; for phone OTP we might have POST /api/auth/send-otp and POST /api/auth/verify-otp). - POST /api/checkout – to handle order creation (this will later integrate with a payment gateway webhook or SDK). - Admin APIs like GET /api/admin/products, POST /api/admin/products for inventory, etc., protected by admin checks.
Each of these will initially contain placeholder logic (e.g., returning mock data or success responses) to allow front-end development and integration testing. This way, the front-end code can call fetch('/api/cart', {method: 'POST', body: ...}) when adding to cart, and we can simulate the behavior until the real backend is ready.
